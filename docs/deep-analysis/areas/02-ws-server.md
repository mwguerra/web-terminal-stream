# 02 — ReactPHP WebSocket server: concurrency & leaks

**Area key:** `ws-server`

## Summary

The ReactPHP server is a single-process, single-threaded event loop (0.01s tick) with reasonable per-session exception isolation inside tick()/handleMessage() (closeSession safety net) and a JSON PID registry for crash cleanup. However the design has several real concurrency/resource-leak defects that matter for a long-running server. The two most serious: (1) the handshake/bridge-start path is NOT guarded, so a single user's SSH auth failure or a proc_open failure throws out of the on('data') callback and takes down the entire loop — every other active terminal dies (DoS from one bad password); (2) dead sessions are never reaped — when the shell exits or SSH drops, tick() just `continue`s past the bridge forever, leaking a zombie child + open FD + registry entry + bridge/buffer memory until the client happens to disconnect. On top of that there is no backpressure (unbounded React write buffering on fast-PTY/slow-client), no max-connection or per-user cap, no handshake-size limit or idle/handshake timeout (unauthenticated memory/FD DoS), PID-reuse risk in the kill-by-pid cleanup, and a Linux-only local path that silently dies on macOS (the dev platform). Registry read-modify-write is safe within one process but races across instances. No graceful-shutdown handler means Ctrl+C orphans every live PTY (setsid detaches them).

## What exists and works

- Per-session exception isolation in tick() and handleMessage(): a throwing bridge is caught and routed to closeSession(), so one dead session does not poison others once it is past the handshake (ReactPhpWebSocketServer.php:231-257, 192-211)
- handleClose() wraps bridge->terminate() in try/catch so a failing teardown cannot break the loop (ReactPhpWebSocketServer.php:213-226)
- Origin allow-list enforced before the single-use token is consumed, so a rejected page cannot burn a stolen token (ReactPhpWebSocketServer.php:109-124)
- Single-use encrypted expiring token with Cache::pull of the connection config (ReactPhpWebSocketServer.php:137-160)
- terminate() does SIGTERM -> 100ms grace -> SIGKILL and closes pipes/proc, and __destruct falls back to terminate() (TerminalPtyBridge.php:238-280)
- SSH interactive channel opened via CHANNEL_SHELL with a real handshake timeout then switched to 0.01s for non-blocking reads inside the loop, with a documented rationale (TerminalPtyBridge.php:117-139)
- Live SSH resize implemented as an RFC4254 window-change channel request rather than the no-op setWindowSize() (InteractiveSsh.php:23-45)
- 60s periodic + on-boot cleanupStale() kills recorded pids that outlive max_session_lifetime, skipping the SSH -1 sentinel via the pid>0 guard (ReactPhpProvider.php:29-35, 74-82)
- Registry save() uses LOCK_EX and JSON, and cleanupStale/unregister keep the file compacted (PtySessionRegistry.php:71-83)

## Gaps (missing functionality)

| Gap | Severity | Detail |
|---|:--:|---|
| No max-connections cap and no per-user session limit | high | The server accepts unbounded WebSocket connections; each authenticated handshake unconditionally spawns a PTY (proc_open or an SSH2 socket) plus a bridge, MessageBuffer, and connection entry. Nothing tracks or limits concurrent sessions per user or globally. The token payload carries userId (ReactPhpWebSocketServer.php:152) but it is only handed to the bridge and never used for accounting. A single authorized user opening tabs in a loop, or a script replaying valid tokens, exhausts PIDs/file descriptors/RAM and can take the host down. FD exhaustion is especially cheap: each session holds a listening WS socket + 3 PTY pipes (or an SSH socket). |
| No handshake size limit and no incomplete-handshake/idle timeout (unauthenticated DoS) | medium | Before the WebSocket upgrade completes there is no auth and no bound: `$httpBuffer .= $data` (ReactPhpWebSocketServer.php:64) grows without limit, so a single client that streams bytes and never sends the terminating CRLFCRLF drives the process to OOM. A connection that simply opens and stays silent is never timed out, holding an FD forever (slowloris). There is no idle timeout anywhere in the server, and no cap on MessageBuffer frame size post-handshake either. Network reachability is a stated boundary, but anyone who can reach the port (misconfigured bind, shared host, SSRF-reachable) needs no token to exhaust memory/FDs. |
| No graceful shutdown: Ctrl+C / SIGTERM orphans every live PTY | medium | TerminalServeCommand advertises 'Press Ctrl+C to stop' and ReactPhpProvider::stop() just calls Loop::get()->stop(), but nothing registers a SIGINT/SIGTERM handler that walks the active bridges and terminate()s them. Because local shells are launched with setsid (new session, TerminalPtyBridge.php:76-77) they are detached from the server and survive its death, so a normal operator restart leaks every currently-connected shell as an orphan. Those orphans are then only reaped by the pid-based cleanupStale pass once they exceed max_session_lifetime (default 3600s), and only if the pid check succeeds — see the pid-reuse and 'fresh orphan' flaws. |
| Local PTY path is Linux-only and silently fails on macOS (the dev platform) | medium | startLocal() shells out to `setsid {shell} -il` (TerminalPtyBridge.php:76-77) and resize() depends on `/proc/<pid>/fd/0` readlink + `stty -F` + `posix_kill(-$pid, SIGWINCH)` (TerminalPtyBridge.php:212-220) — all Linux-specific. macOS has no default `setsid` binary and no /proc, so on macOS the local terminal process dies immediately (sh: setsid: command not found) and resize is a permanent no-op. There is no capability probe or error surfaced; the only acknowledgement is a docs line and a Linux-only integration test group. The dev machine here runs macOS, so 'works on my machine' local testing of the local path is impossible without a Linux container. |
| Registry read-modify-write is not atomic across processes | low | register/unregister/cleanupStale each do all() (read whole file) then save() (LOCK_EX write). LOCK_EX only serializes the write, not the read-modify-write cycle. This is safe inside one event loop (timers/callbacks never interleave), but two serve processes sharing storage/web-terminal-stream/pty-sessions.json (e.g. running a second instance on another port, as the docs suggest for coexistence) will lose registrations and can cross-kill each other's sessions during cleanupStale. Not the documented single-process deployment, but the shared file path invites it. |

## Flaws (implemented but wrong/risky)

Each critical/high flaw was handed to an independent skeptic instructed to refute it.

### Uncaught exception during handshake/bridge-start crashes the entire event loop (one bad SSH password kills all sessions)
- **Severity:** critical — **Verdict:** ✅ confirmed
- **Files:** src/WebSocket/ReactPhpWebSocketServer.php, src/WebSocket/TerminalPtyBridge.php
- **Detail:** handleHandshake() calls $bridge->start($shell) with no try/catch (ReactPhpWebSocketServer.php:169-170). start() -> startSsh() throws RuntimeException on SSH auth failure (TerminalPtyBridge.php:109, 114) and startLocal() throws on proc_open failure (TerminalPtyBridge.php:85). That throwable propagates out of the on('data') closure (ReactPhpWebSocketServer.php:61-72), which React's stream emitter does not catch, so it becomes a fatal uncaught exception that terminates Loop::run() — killing the server and every other connected terminal. Unlike tick()/handleMessage(), the handshake path has no safety net. A single user submitting a wrong SSH password (or a transient proc_open ENOMEM/EMFILE) is a full-service DoS.
- **Evidence:** ReactPhpWebSocketServer.php:169-170 (`$bridge = new TerminalPtyBridge(...); $bridge->start($shell);` — no surrounding try/catch, whereas lines 199-210 and 234-255 are guarded). Throw sites: TerminalPtyBridge.php:85 (proc_open fail), :109 ('SSH key authentication failed'), :114 ('SSH password authentication failed'). ### Dead PTY sessions are never reaped — zombie child + open WS + stale registry entry leak until the client disconnects
- **Severity:** high — **Verdict:** ✅ confirmed
- **Files:** src/WebSocket/ReactPhpWebSocketServer.php, src/WebSocket/TerminalPtyBridge.php
- **Detail:** In tick(), `if (! $bridge->isRunning()) { continue; }` (ReactPhpWebSocketServer.php:235-237) simply skips any bridge whose shell has exited or whose SSH transport dropped. Nothing ever calls terminate()/proc_close() or closes the WS for that session. So when a user types `exit` (a common path) or the remote SSH drops: (a) the sh/bash child becomes a defunct zombie because proc_close (which waitpid-reaps) is never called; (b) the WS connection and its 3 pipes / SSH socket stay open holding FDs; (c) the bridge, MessageBuffer and connection stay in the arrays holding memory; (d) the registry entry remains. These accumulate for the entire lifetime of the long-running server whenever a client leaves the tab open. The 60s cleanupStale cannot help — it only fires after max_session_lifetime (1h) and posix_kill on a zombie is a no-op (only proc_close reaps it). The server should detect !isRunning() and closeSession() it.
- **Evidence:** ReactPhpWebSocketServer.php:233-237 — the loop `continue`s on !isRunning() instead of tearing the session down; there is no other place that observes shell exit. isRunning() is proc_get_status()['running'] for local (TerminalPtyBridge.php:223-236) / sshShell->isConnected() for SSH. proc_close (the only reap path) is only in terminate() (TerminalPtyBridge.php:267), which this branch never calls.
- **Verifier:** PARTIALLY REAL, but the headline mechanism (zombie accumulation) is FALSE and the severity is overstated.

CONFIRMED TRUE (the real defect): tick() does `if (! $bridge->isRunning()) { continue; }` (ReactPhpWebSocketServer.php:235-237) and there is genuinely no other code path that observes shell/SSH

### No backpressure: unbounded WebSocket write buffering on fast PTY vs slow client
- **Severity:** high — **Verdict:** ✅ confirmed
- **Files:** src/WebSocket/ReactPhpWebSocketServer.php, src/WebSocket/TerminalPtyBridge.php
- **Detail:** Each tick, read() drains ALL currently-available PTY output — the local path loops fread(8192) until the pipe is empty (TerminalPtyBridge.php:166-178) with no per-tick cap — then tick() does `$conn->write($frame->getContents())` (ReactPhpWebSocketServer.php:239-249). React's ConnectionInterface::write() buffers in-process memory without bound when the socket cannot drain (slow/stalled browser, e.g. a backgrounded tab). A flood command (`yes`, `cat bigfile`, `find /`) produces output far faster than a slow client consumes it, so the React write buffer grows unbounded → RSS blowup / OOM of the shared server. There is no check of write()'s return value, no pause of PTY reads while the socket buffer is high, and no drain('drain') handling. The OS PTY buffer backpressures the shell, but the unbounded growth is on the WS-write side, in the one process that serves every session.
- **Evidence:** ReactPhpWebSocketServer.php:239-249 (write with no return-value/backpressure check); TerminalPtyBridge.php:166-178 (read() loops until the pipe is empty, no cap). No calls to pause()/resume() or 'drain' anywhere in src/WebSocket.
- **Verifier:** The code claims hold exactly as described. TerminalPtyBridge::read() (src/WebSocket/TerminalPtyBridge.php:166-178) drains both PTY pipes fully each call via `while ((fread($pipe,8192)) !== false && $chunk !== '')` with no per-tick cap. tick() (src/WebSocket/ReactPhpWebSocketServer.php:239-248), fire

### PID-reuse: stale cleanup blindly SIGKILLs a recorded pid whose number may now belong to an unrelated process
- **Severity:** medium — **Verdict:** ⚪ unverified
- **Files:** src/WebSocket/ReactPhpProvider.php, src/WebSocket/PtySessionRegistry.php
- **Detail:** cleanupStale returns entries older than max_session_lifetime and the caller does `if ($session['pid'] > 0 && posix_kill($pid, 0)) posix_kill($pid, 9)` (ReactPhpProvider.php:31-35 and 77-81). posix_kill($pid,0) only proves *some* process holds that pid, not that it is still our shell. After a crash+reboot, or simply after >1h on a busy host, the OS recycles pids, so the recorded number can now be an unrelated (possibly important) process that the cleanup pass then SIGKILLs. The registry stores only a raw pid + createdAt with no start-time/uid re-validation, so there is no way to detect reuse.
- **Evidence:** src/WebSocket/ReactPhpProvider.php:31-35 and :77-81 (kill-by-pid with only a posix_kill(,0) liveness check); PtySessionRegistry.php:16-25 stores {pid,userId,createdAt} with no pid-start-time or command fingerprint.

### Crash orphans younger than max_session_lifetime are not cleaned on restart
- **Severity:** medium — **Verdict:** ⚪ unverified
- **Files:** src/WebSocket/PtySessionRegistry.php, src/WebSocket/ReactPhpProvider.php
- **Detail:** Because local shells are setsid-detached they survive a server crash/SIGKILL as reparented orphans. The on-boot cleanup only kills entries where `now - createdAt > max_session_lifetime` (PtySessionRegistry.php:59-64), default 3600s. So a shell orphaned 5 minutes before a crash is NOT killed when the server restarts — it keeps running (consuming CPU/RAM, e.g. a `top` or `tail -f`) for up to an hour, and its registry entry lingers. The documented promise ('on the next server start ... SIGKILLs any recorded pid that is still alive', README.md:754-755 / architecture.md:85) overstates behavior: only *expired* pids are killed on startup, not all live recorded pids. Fresh orphans slip through the exact window a crash-recovery pass is supposed to cover.
- **Evidence:** src/WebSocket/PtySessionRegistry.php:59-64 (only entries past maxLifetime are collected as stale); ReactPhpProvider.php:29-35 (startup pass iterates only that stale set). Contrast README.md:754-755 which claims live recorded pids are killed on startup.
