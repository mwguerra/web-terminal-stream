# 04 — End-to-end terminal lifecycle flows

**Area key:** `flows`

## Summary

Mapped all 8 end-to-end terminal lifecycle flows. The happy paths are coherent and the client/server contract (token issuance -> single-use Cache::pull -> PTY bridge -> 10ms tick streaming -> resize -> teardown) is largely sound and matches the documented architecture. The dominant problem is that ReactPhpWebSocketServer::handleHandshake runs bridge startup (and a null-int cast) with NO exception guard inside the ReactPHP 'data' callback: an SSH auth failure, a guest/null userId, or a proc_open failure throws an uncaught exception that propagates out of Loop::run() and kills the entire long-running server — dropping every other user's live session. SSH connect is also performed synchronously inside the handshake, freezing all sessions for up to the SSH timeout. Secondary issues: dead shells (user types `exit`) are never closed server-side so the client stays falsely "connected" and bridges leak; disconnect logging/events are unreliable on SPA navigation and pane close; and the Livewire getWebSocketUrl() hardcodes ws:// which is mixed-content-blocked on HTTPS pages unless websocket_url is manually set (the controller path gets this right, the primary path does not).

## Gaps (missing functionality)

| Gap | Severity | Detail |
|---|:--:|---|
| Shell exit (`exit` / crash) never closes the WebSocket — dead bridges leak and client shows false 'connected' | medium | In ReactPhpWebSocketServer::tick(), when a bridge's shell process exits, bridge->isRunning() returns false and the loop just `continue`s (line 235-237). Nothing ever closes the connection for that dead session. Consequences: (1) the browser terminal remains visually 'connected' with a frozen dead shell and no signal that the session ended; (2) the TerminalPtyBridge + connection + buffer stay in the server's arrays (memory leak / registry entry lingers) until the client eventually navigates away or max_session_lifetime cleanup fires up to 1 hour later. The server should detect isRunning()===false during tick and proactively closeSession($id). |
| Disconnect event + log row missing on SPA navigation and pane close (most common exit paths) | medium | resources/views/stream-terminal.blade.php destroy() (lines 260-283) is the handler for beforeunload/pagehide/livewire:navigating and for nested-component teardown (workspace/dashboard pane close). It closes the WebSocket but never calls $wire.disconnect(), and the Livewire component is being destroyed so no round-trip can complete. Therefore TerminalDisconnectedEvent and TerminalLogger::logDisconnection are skipped for navigating away and for closing a pane — the two most frequent ways a session ends. terminal_stream_logs accumulates CONNECTED rows with no matching DISCONNECTED row, and getSessionSummary() computes an open-ended duration to now(). Because the server manages the PTY teardown but writes no logs, there is no reliable source for the disconnect record. |
| max_session_lifetime cleanup kills the PID but leaves the WebSocket/bridge open | low | ReactPhpProvider's 60s periodic timer calls registry->cleanupStale() and posix_kill(-9) on PIDs older than max_session_lifetime (default 3600s), but it operates only on the JSON registry and raw PIDs — it does not close the corresponding open WebSocket or remove the bridge from ReactPhpWebSocketServer's live arrays. A legitimately long-running interactive session is therefore killed underneath a still-open socket, leaving the user with a frozen terminal and no disconnect signal, and the dead bridge lingering in server memory. Teardown is half-done: process death is not reflected to the transport layer. |

## Flaws (implemented but wrong/risky)

Each critical/high flaw was handed to an independent skeptic instructed to refute it.

### Uncaught exception during handshake/bridge-start crashes the entire WebSocket server for ALL sessions (trivial DoS)
- **Severity:** critical — **Verdict:** ✅ confirmed
- **Files:** src/WebSocket/ReactPhpWebSocketServer.php, src/WebSocket/TerminalPtyBridge.php, src/Livewire/StreamTerminal.php
- **Detail:** ReactPhpWebSocketServer::handleHandshake (called synchronously from the connection's 'data' callback) runs bridge->start($shell) at line 170 with NO try/catch. ReactPHP's StreamSelectLoop does not wrap stream read listeners in try/catch, so any of these exceptions propagates out of Loop::run() and terminates the whole long-running server process — dropping every other connected user's live PTY session. The 101 Switching Protocols response was already written (line 163) and the config already Cache::pull'd, so the client believes it connected right as the server dies. ### SSH connection is performed synchronously inside the handshake, freezing all other sessions
- **Severity:** high — **Verdict:** ✅ confirmed
- **Files:** src/WebSocket/TerminalPtyBridge.php, src/WebSocket/ReactPhpWebSocketServer.php, src/WebSocket/ReactPhpProvider.php
- **Detail:** TerminalPtyBridge::startSsh() runs InteractiveSsh::login() (full TCP connect + DNS + KEX + auth) and write('', CHANNEL_SHELL) synchronously, and it is invoked from handleHandshake which runs inside the single shared ReactPHP event loop (ReactPhpProvider registers one loop with a 10ms tick). While an SSH connection is being established, tick() cannot run and no other terminal receives output — every other user's session is frozen for the full duration of the SSH connect. For a slow or unreachable host this is up to the configured timeout (setTimeout(max(5, timeout)) = 5-10s+, plus TCP connect time). This turns one user's SSH attempt to a laggy host into a service-wide stall. SSH setup should be performed off the loop (async connector / deferred) rather than blocking the handshake.
- **Evidence:** src/WebSocket/TerminalPtyBridge.php:95-139 (synchronous login + write CHANNEL_SHELL, setTimeout(max(5,timeout))) invoked from src/WebSocket/ReactPhpWebSocketServer.php:170 inside the 'data' callback ; single loop with 10ms tick in src/WebSocket/ReactPhpProvider.php:70-72,84.
- **Verifier:** Confirmed. The SSH connect is genuinely synchronous and inline in the single shared ReactPHP loop. ReactPhpProvider.php:43-84 runs one Loop::get() with a 10ms periodic tick (70-72). ReactPhpWebSocketServer.php:61-65 invokes handleHandshake from the connection's 'data' callback, and line 170 calls $b

### getWebSocketUrl() hardcodes ws:// and is mixed-content-blocked on HTTPS pages
- **Severity:** medium — **Verdict:** ⚪ unverified
- **Files:** src/Livewire/StreamTerminal.php, src/Http/Controllers/TerminalWebSocketController.php, config/web-terminal-stream.php
- **Detail:** StreamTerminal::getWebSocketUrl() (the primary Livewire path used by every WebTerminalStream/workspace/dashboard pane) builds the URL as "ws://{host}:{port}?token=..." whenever stream.websocket_url is not set (line 124-126). On a production HTTPS page, a browser blocks a ws:// connection to a non-TLS endpoint as mixed/insecure content, so the terminal silently fails to connect (ws.onerror only console.errors). Notably the alternative TerminalWebSocketController::generateToken() DOES pick the scheme correctly via $request->isSecure() ? 'wss' : 'ws' (line 34,38), so the two token-issuance paths are inconsistent, and the one actually wired into the components is the broken one. Deployments must manually set WEB_TERMINAL_STREAM_WEBSOCKET_URL to a wss:// URL or the terminal is dead on HTTPS; getWebSocketUrl should derive wss from request()->isSecure() (or from the configured ssl_cert/ssl_key) like the controller does.
- **Evidence:** src/Livewire/StreamTerminal.php:119-127 (ws:// hardcoded when websocket_url empty) vs src/Http/Controllers/TerminalWebSocketController.php:34,38 ($request->isSecure() ? 'wss' : 'ws'). Client surfaces failure only via ws.onerror console.error in resources/views/stream-terminal.blade.php:164-166.

### $wire.connect() fires events + writes log rows with no authorization check
- **Severity:** low — **Verdict:** ⚪ unverified
- **Files:** src/Livewire/StreamTerminal.php
- **Detail:** StreamTerminal::connect() (lines 136-167) dispatches TerminalConnectedEvent and calls TerminalLogger::logConnection with no gate check, unlike getWebSocketUrl() which gates on useStreamTerminal (line 100). Any user with the page loaded can invoke $wire.connect()/$wire.disconnect() directly (public Livewire methods) to emit fabricated connect/disconnect events and pollute terminal_stream_logs without ever opening a WebSocket or PTY. Page-level authz limits the blast radius, but the connection audit trail can be forged/spammed by an authorized page viewer independent of actual terminal access. If getWebSocketUrl returned 'Unauthorized', connect() still logs a connection.
- **Evidence:** src/Livewire/StreamTerminal.php:136-167 (connect: no Gate) vs :100-102 (getWebSocketUrl: Gate::has/allows('useStreamTerminal')). Logging via :160 getLogger()->logConnection.

### Local PTY start and resize are silently Linux-only (broken on macOS/BSD dev and non-Linux hosts)
- **Severity:** medium — **Verdict:** ⚪ unverified
- **Files:** src/WebSocket/TerminalPtyBridge.php
- **Detail:** startLocal() runs proc_open("setsid {$shell} -il", ...) — 'setsid' is not a shipped binary on macOS, so on the darwin dev machine sh -c fails to exec it and the shell dies immediately while proc_open still returns a valid resource (no RuntimeException, so the failure is invisible; the client just sees an empty/closing terminal). resize() reads /proc/<pid>/fd/0 and shells out to stty (TerminalPtyBridge:212-217), both Linux-only; off Linux readlink fails and only posix_kill(-pid, SIGWINCH) is sent against an unchanged kernel window size. There is no capability check or error surfaced for either. The package targets Linux servers, but nothing guards or documents the hard coupling, and the project's own dev/e2e workstation is darwin.
- **Evidence:** src/WebSocket/TerminalPtyBridge.php:76-82 (setsid + proc_open, no exec-failure detection) ; :210-220 (/proc/<pid>/fd/0 readlink + stty + SIGWINCH).
