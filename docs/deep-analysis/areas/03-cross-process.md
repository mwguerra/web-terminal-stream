# 03 — Cross-process token/cache/config correctness

**Area key:** `cross-process`

## Summary

The HTTP↔serve contract is fundamentally sound: both sides derive the token cipher from the same app('encrypter') (StreamTerminal.php:116 / TerminalWebSocketController.php:30 → ReactPhpProvider.php:39 → ReactPhpWebSocketServer.php:138), so the shared-APP_KEY assumption holds as long as serve runs in the same app/.env. The single-use handoff is correct: Cache::put with TTL=signed_url_ttl on the HTTP side (StreamTerminal.php:108) and Cache::pull on the server (ReactPhpWebSocketServer.php:155) give exactly-once consumption; the token exp (StreamTerminal.php:113) is checked against the server clock (ReactPhpWebSocketServer.php:145) and is aligned with the cache TTL, and stream.* config is read identically in both processes. The requirement is documented (architecture.md:19-24, README.md:110/738). The weak seams are all around the SHARED-CACHE assumption and URL construction: (1) nothing validates or warns that the default cache store is a shared persistent one — an array/per-process store silently makes every connection close with zero diagnostics; and (2) the HTTP token controller ignores stream.websocket_url and hardcodes ratchet_host/port, so proxied/TLS custom frontends get an unreachable URL, diverging from the Livewire path. Session-id leakage on never-opened tokens is real but self-healing at TTL and intentional (single-use).

## What exists and works

- Token cipher symmetry: both HTTP paths encrypt with app('encrypter') (StreamTerminal.php:116, TerminalWebSocketController.php:30) and the serve process decrypts with the same encrypter injected via ReactPhpProvider.php:39 → ReactPhpWebSocketServer.php:138 — the shared-APP_KEY contract is honored when serve runs in the same app/.env.
- Single-use config handoff is correct: Cache::put (StreamTerminal.php:108 / TerminalWebSocketController.php:22) paired with Cache::pull (ReactPhpWebSocketServer.php:155) gives exactly-once retrieval; a replayed token finds an empty slot and the connection is closed (ReactPhpWebSocketServer.php:156).
- Token exp and cache TTL are both derived from stream.signed_url_ttl (StreamTerminal.php:106/113, controller:19/27) so the token cannot outlive its cached config; server enforces exp against its own clock (ReactPhpWebSocketServer.php:145).
- Config is read consistently from web-terminal-stream.stream.* in both processes (ReactPhpProvider.php:23 reads the same block the HTTP side reads), and cache key prefix terminal-stream-pty:{sessionId} is identical on both sides.
- Livewire URL path honors stream.websocket_url as an explicit proxy/TLS override before falling back to ratchet_host/port (StreamTerminal.php:119-127).
- Cross-process requirement is documented (architecture.md:19-24 'must run inside the same application (same .env)'; README.md:110/738 troubleshooting).

## Gaps (missing functionality)

| Gap | Severity | Detail |
|---|:--:|---|
| serve never validates that the cache store is shared/persistent — array or per-process cache silently breaks every connection with no diagnostic | medium | The whole HTTP→serve handoff rides on Cache::put (StreamTerminal.php:108) and Cache::pull (ReactPhpWebSocketServer.php:155) hitting the SAME shared store. Both calls use the default cache store — there is no dedicated store config and no store selection anywhere in src/. If the app's default cache resolves to the 'array' driver (Laravel's testing default, and easy to land in via CACHE_STORE=array) or any per-process/in-memory store, the serve process has its own separate cache: every Cache::pull returns null, and ReactPhpWebSocketServer.php:156 closes the socket immediately. The failure is completely silent — the WebSocket opens, gets no upgrade, and closes; the user sees a terminal that never connects with no server-side log line explaining why. TerminalServeCommand::handle() (TerminalServeCommand.php:28-46) prints only 'Starting WebSocket server' and does no environment sanity check. The contract is mentioned only in README troubleshooting (README.md:738), never enforced. A one-line check in serve — resolve config('cache.default'), and warn/refuse if it is 'array' (or more generally if the resolved store is an ArrayStore) — would turn a silent, hard-to-diagnose outage into an actionable startup warning. Same argument for warning when APP_KEY is unset. |
| No safeguard against long-running serve holding stale in-memory config/APP_KEY after a rotation or config change | low | ReactPhpProvider::start() snapshots config once (ReactPhpProvider.php:23) and captures $this->app['encrypter'] once (ReactPhpProvider.php:39) for the life of the process. Because serve is a long-running daemon, an APP_KEY rotation or any config:cache change in the HTTP app is not picked up until serve is restarted — after an APP_KEY rotation the HTTP side issues tokens under the new key while serve still decrypts with the old one, so every handshake fails decryption (ReactPhpWebSocketServer.php:138-143) until a manual restart. This is inherent to daemonized Laravel, but it is undocumented as an operational constraint and there is no version/keys-match handshake to surface the mismatch. |

## Flaws (implemented but wrong/risky)

Each critical/high flaw was handed to an independent skeptic instructed to refute it.

### TerminalWebSocketController ignores stream.websocket_url and hardcodes ratchet_host/port — returns an unreachable URL for proxied/TLS custom frontends
- **Severity:** medium — **Verdict:** ⚪ unverified
- **Files:** src/Http/Controllers/TerminalWebSocketController.php, src/Livewire/StreamTerminal.php
- **Detail:** The HTTP token endpoint builds the WebSocket URL as {protocol}://{ratchet_host}:{ratchet_port} using only stream.ratchet_host (default 127.0.0.1) and stream.ratchet_port, with protocol chosen from $request->isSecure() (TerminalWebSocketController.php:32-38). It never reads stream.websocket_url. This diverges from the Livewire path (StreamTerminal.php:119-127), which correctly prefers websocket_url as the proxy/TLS override. Consequence: a deployment that sets WEB_TERMINAL_STREAM_WEBSOCKET_URL=wss://your-domain/terminal-ws (the documented reverse-proxy setup, README.md:145-170) and drives a custom (non-Livewire) frontend through POST terminal-stream/ws-token gets back wss://127.0.0.1:8090 — pointing at the internal bind address, unreachable from the browser, and with the wrong host even under Direct TLS where the public host is not 127.0.0.1. The two token-issuance paths must construct the URL identically; the controller should reuse the same websocket_url-first logic.
- **Evidence:** TerminalWebSocketController.php:32-38 constructs "{$protocol}://{$host}:{$port}" from ratchet_host/ratchet_port only, with no reference to config('web-terminal-stream.stream.websocket_url'); compare StreamTerminal.php:119-127 which reads websocket_url first.

### Livewire URL fallback always emits ws:// (never wss://) even when the server is configured for direct TLS (ssl_cert/ssl_key set)
- **Severity:** low — **Verdict:** ⚪ unverified
- **Files:** src/Livewire/StreamTerminal.php, src/WebSocket/ReactPhpProvider.php, config/web-terminal-stream.php
- **Detail:** When stream.websocket_url is unset, getWebSocketUrl hardcodes the scheme to ws:// (StreamTerminal.php:126) regardless of page security or whether stream.ssl_cert/ssl_key are configured — i.e. even when ReactPhpProvider.php:49-58 is actually serving tls://. On an HTTPS Filament page this yields a mixed-content ws:// URL that the browser blocks, and enabling ssl_cert alone (without also setting websocket_url) produces a ws:// URL that cannot reach the tls:// server. Unlike the controller, this path does not even consult request security. This is DOCUMENTED as requiring a manual websocket_url override (README.md:165-170 shows SSL_CERT paired with WEBSOCKET_URL; README.md:746 troubleshooting), so it is a known/intentional sharp edge rather than a hidden bug — but the default remains a broken URL under the common HTTPS deployment, and the code could auto-derive wss:// when ssl_cert/ssl_key are present.
- **Evidence:** StreamTerminal.php:123-126: else branch builds "ws://{$host}:{$port}?..." with a literal ws:// scheme and no check of ssl_cert/ssl_key or request()->isSecure(); ReactPhpProvider.php:49 switches the actual socket to tls:// when those certs exist.

### Never-opened token leaks its cached config entry until TTL; repeated getWebSocketUrl calls orphan extra entries
- **Severity:** low — **Verdict:** ⚪ unverified
- **Files:** src/Livewire/StreamTerminal.php, src/WebSocket/ReactPhpWebSocketServer.php
- **Detail:** Each getWebSocketUrl() call writes a fresh terminal-stream-pty:{sessionId} entry (StreamTerminal.php:104-108) and overwrites $this->sessionId. If the browser never opens the WebSocket (Manual pane not clicked, tab closed, reconnect flow re-issuing), the entry is never Cache::pull-ed and lingers for the full signed_url_ttl (300s). Under a reconnecting Auto pane this can accumulate several orphaned entries per component before they expire. Impact is minor: entries are small, TTL-bounded, and the single-use design intends leftover slots to simply expire — noting it as a known, self-healing leak rather than a correctness bug. No enforcement of one-outstanding-token-per-component exists.
- **Evidence:** StreamTerminal.php:104-108 unconditionally generates a new uuid and Cache::put on every call; the only consumer is Cache::pull at ReactPhpWebSocketServer.php:155 which fires only when a WS actually opens.
